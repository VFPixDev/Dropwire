# Систематический аудит Dropwire — 12 ноября 2026

Первый проход был направлен на три присланные ошибки и ближайшие ветки
обработки. Этот проход выполнен отдельно по структуре приложения и его
границам доверия. Он охватывает конфигурацию, обработчики, провайдеры,
БД, файлы, веб-сервис, конкурентную обработку, сборку и зависимости.

Этот проход выполнен тем же исполнителем. Независимое ревью GitHub
Codex выполнено позднее в PR #29; дополнение приведено ниже. Производственные логи,
состояние рабочего сервера и отправка сообщений в рабочие чаты не
использовались.

## Новые подтверждённые проблемы и исправления

| № | Проблема и условие воспроизведения | Исправление |
| --- | --- | --- |
| 1 | При непустом whitelist и пустом `BOT_ADMIN_IDS` все разрешённые пользователи получали права владельца | Whitelist и владельцы полностью разделены. Регрессионный тест читает реальную конфигурацию из окружения |
| 2 | Изменение прав уже добавленного бота записывало инициатора как нового постоянного «добавившего бота» | Такая привязка создаётся только при переходе бота из неактивного состояния в активное; ограниченный пользователь вне группы не проходит проверку членства |
| 3 | HTTP-логи и исключения могли содержать ключ YouTube, токен Telegram и подписанные ссылки | Добавлен форматтер, редактирующий секреты в сообщениях и traceback; шум HTTP-клиентов отключён. Изменено диагностическое чтение Telegram, чтобы не выводить URL с токеном при сетевой ошибке |
| 4 | Старой кнопкой отмены можно было переписать состояние уже начатой или завершённой загрузки | Отмена допускается только для `pending/queued`. Начало работы атомарно переводит только `queued` в `downloading`, поэтому отменённый запрос не возобновляется |
| 5 | Незавершённый выбор качества бессрочно занимал пользовательский лимит | Запросы `pending` старше часа освобождаются при резервировании и периодической очистке |
| 6 | Готовый файл удалялся при сетевой ошибке отправки ссылки или ошибке после успешной отправки | Файл сначала регистрируется и сохраняется в состоянии `ready`; при неудаче уведомления он остаётся доступен через `/downloads` |
| 7 | Удалённое сообщение прогресса или запрет его редактирования мог оборвать загрузку | Прогресс стал необязательным: недоступность сообщения отключает обновления, но не работу. Текст прогресса отправляется без HTML-разбора |
| 8 | Долгое получение метаданных оставляло callback без своевременного ответа | Callback подтверждается сразу. Истёкший повторный ответ не превращает успешно выполненное действие в необработанное исключение |
| 9 | Очередь ограничивала работающие скачивания, но не общий размер ожидания | Добавлен общий предел 32 ожидающих заданий и понятный отказ с освобождением запроса. При остановке новые задачи запрещаются, ожидающие отменяются, активные завершаются |
| 10 | После таймаута inline-запроса shield-задача продолжалась уже вне семафора | Лимит находится внутри фоновой загрузки и действует всё время её работы; число фоновых запросов также ограничено |
| 11 | Несколько одновременных запросов одного файла загружали его в технический канал несколько раз | Подготовка объединяется по БД и URL; используется одна общая фоновая задача. Фоновые задачи медиакэша имеют общий предел |
| 12 | При завершении приложения БД и Telegram-сессия закрывались раньше фоновых задач | Добавлен упорядоченный shutdown: очередь, inline, медиакэш, БД, сессия. Настоящий лимит задач задан и в polling, чтобы не накапливать неограниченное число ожидающих обработчиков |
| 13 | Проверка размера oEmbed/Spotify выполнялась после полного чтения, а YouTube не имел аналогичного ограничения | Все эти ответы читаются потоково до установленного лимита; отдельно проверяется размер распакованного тела |
| 14 | FxTwitter-ответ мог повторно распаковываться при сохранении `Content-Encoding` после `aiter_bytes()` | При построении прочитанного ответа удаляются заголовки уже обработанного кодирования и старой длины |
| 15 | Повреждённый URL мог оборвать поиск всех ссылок; YouTube проверял домен удалением всех `www.` | Парсинг повреждённых URL безопасен, домены проверяются точно, учётные данные и неожиданные порты отвергаются. Twitter-нормализация проверяет домен и поддерживает `/i/web/status/...` |
| 16 | Скачиваемые rich-видео обходили настройку `MAX_MEDIA_MB`; конвертация и очистка временных результатов были непоследовательны | Заданный лимит применяется к скачиванию видео и подготовке файлов для прямой загрузки. Повторная загрузка использует общий фоновый процесс подготовки, совместимые кодеки и реальные размеры. Неуспешные временные результаты удаляются |
| 17 | Silent-video отклонялось из-за отсутствия AAC, хотя аудиодорожка необязательна; не учитывался SAR | Видео без аудио разрешено, аудио при наличии проверяется на AAC. Пропорции нормализуются с учётом SAR и `setsar=1` |
| 18 | Очистка могла удалить старую папку активного задания; отмена coroutine не останавливала работающий поток; поздний прогресс мог прийти после результата | Активные пути исключены из очистки. Поток получает сигнал остановки и завершается до удаления файлов. Перед возвратом результата ожидаются отправленные обновления прогресса |
| 19 | JSON-путь Twitter не переносил опрос в модель, поэтому успешный API-ответ терял варианты | Добавлен разбор вариантов, голосов, процентов и состояния опроса; его вопрос не дублируется, если отдельно отсутствует |
| 20 | `MODE=webhook` принимался, хотя запуск всегда выполнял polling; `NaN/Infinity` проходили проверку таймаутов | Неподдерживаемый режим и неконечные значения отклоняются при загрузке конфигурации |
| 21 | Ошибка необязательного запроса YouTube-канала отменяла уже полученную карточку видео; короткий Spotify-токен мог кэшироваться дольше своего срока | Для канала используется доступное название; кэш Spotify учитывает короткий срок токена |
| 22 | Повторная Docker-сборка использовала устаревший слой `apk upgrade` | Системный слой выделен в стадию `system`. CI и release обновляют её без кэша; команды локальной сборки обновлены. CI сканирует High и Critical |

## Проверка образа

Trivy обнаружил в старом системном слое 33 находки по пакетам: одну
Critical и 32 High, соответствующие 18 уникальным CVE. Среди затронутых
компонентов: Brotli, Expat, musl, libX11, PCRE2, zlib и библиотеки util-linux.
Это находки сканера по версиям компонентов, а не доказательство эксплуатации.

После обновления системных пакетов и пересборки повторный Trivy-скан
завершился успешно: **0 High/Critical**. Pillow уже обновлён в первом проходе;
`pip-audit --local` также не находит известных уязвимостей в проверенном
Python-окружении.

Машиночитаемые результаты находятся в `.pytest_cache/trivy-before.json`
и `.pytest_cache/trivy-after.json`. В отчёт не включены секреты `.env`.

## Результаты проверок

- **175 тестов прошли.** 32 новых сценария второго прохода находятся в `tests/test_system_audit.py`; дополнительно сохранены 24 регрессионных сценария первого прохода, добавлены 5 проверок сохранности вложений по замечанию Codex и 17 сценариев маршрутизации групповых ответов.
- Ruff, Bandit, `pip check`, `git diff --check`, Compose validation — успешно.
- Trivy по обновлённому Linux-образу — 0 High/Critical; Python-аудит — без известных уязвимостей.
- Живые запросы Twitter, YouTube, Spotify, SoundCloud и Telegram `getMe` — успешно.
- YouTube-скачивание с конвертацией в 360p в новом контейнере — успешно.
- `scripts/smoke_media.py`: реальный FFmpeg проверил silent-video, нормализацию SAR и подготовку Telegram-видео — успешно.
- HTTP-тест веб-сервиса проверил `206 Partial Content`, точные байты диапазона и отказ по недействительному/истёкшему токену.

## Ограничения вывода

Аудит и тесты не доказывают отсутствие всех возможных ошибок. Новые
отправки в Telegram проверялись с имитацией отказов API; сообщения в
рабочие чаты не отправлялись. Не проверялись интерфейсы всех версий
клиентов Telegram, рабочая nginx-конфигурация и состояние удалённого
сервера. Образ проверен на локальной Linux-архитектуре; multi-arch
публикация не выполнялась.

Изменения находятся в рабочем дереве и локальном образе `dropwire:audit`.
Рабочий бот не развёртывался и не перезапускался.

## Дополнение по независимому ревью PR

В PR #29 GitHub Codex обнаружил риск удаления пользовательского вложения
при обработке ссылки в подписи. Автоматическое удаление теперь разрешено
только для текстовых исходных сообщений. Фото, видео, документы, анимации
и аудио с обработанной ссылкой в подписи сохраняются. Это проверено
отдельными регрессионными сценариями.

## Групповые ответы со ссылкой

До слияния PR добавлено сохранение адресата ответа: если пользователь
отвечает собеседнику ссылкой, при включённом «Отвечать реплаем» карточка
бота отвечает на то же сообщение. Настройка «Удалять исходное» удаляет
только текст пользователя со ссылкой после успешной обработки. Топик и
авторство запроса для `/del` сохраняются. Служебный автоматический ответ
на корень топика не считается явным ответом собеседнику. Если адресат
уже удалён, Telegram разрешено отправить карточку без привязки ответа.
